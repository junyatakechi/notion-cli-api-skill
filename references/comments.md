# コメントの取得と返信（返信は頼まれたときだけ）

ユーザーや他のスキルからページを渡されてコメントを扱うときの一連。
**既定は取得して内容を伝えるところまで**で、返信は明示されたときだけ行う。
ここが持つのは取り方と返し方で、**何と答えるか**は呼び出し側の判断。

## このスキルで公式MCPを使う例外（先に読む）

このスキルの本分はREST APIへの薄いアクセスで、**コメントも取得・返信ともRESTが既定**。
公式MCPを使うのは下の3つだけで、どれもRESTでは代わりが効かない理由がある。

| 場面 | 使うMCPのツール | RESTで済ませない理由 |
|---|---|---|
| **コメントの取得で、効率を重視するよう頼まれたとき** | `notion-get-comments` | RESTはブロック単位でしか返さず、ページ全体ではブロック数ぶん問い合わせる（228ブロックで約2分） |
| 解決済みのコメントを読むとき | `notion-get-comments(include_resolved=true)` | RESTは仕様上、未解決しか返さない |
| 返信するスレッドを絞るため、使い手本人のIDを知るとき | `notion-get-users(user_id="self")` | RESTのトークンはIntegrationなので、`GET /users/me` はbotを返す |

**返信は例外なくREST。** MCPの `notion-create-comment` は使わない（→ 手順2）。

2026-09-17から取得はMCPで行っていたが、2026-09-29にRESTを既定へ戻した。
スキルの本分はRESTにあり、MCPは速さが要る場面の例外にとどめるため。

## 0. 既定は「取得して内容を伝える」。返信は頼まれたときだけ

- **「返信して」「答えて」と言われない限り返信しない。** 未解決スレッドを取り、
  どの記述への指摘か・誰の発言かを添えて内容を伝えるところまでが既定の振る舞い
- **「拾う」は取得だけを指す。** 呼び出し側やユーザーが「拾って」とだけ言ったときは返信しない
- 返信を頼まれたら、自分宛てのスレッド（→ 1-3）**全件**へ返す。答えが決め切れないスレッドも
  飛ばさず、分かる範囲の回答と、確認したい点を書いて返す
- 終わったら**取得件数を報告する**。返信したときは**返信件数**も添える（数が合わなければ取りこぼしている）

| 言われ方 | すること |
|---|---|
| 「Notionのコメントを拾って」「コメントを拾っておいて」 | 取得 → **内容を伝える（返信しない）** |
| 「ページのコメントを見て」「指摘を拾って」 | 取得 → **内容を伝える（返信しない）** |
| 「コメントに答えて」「コメントに返信して」「拾って返信して」 | 取得 → **自分宛ての全件へ返信** |

2026-10-01に、既定を「全件へ返信」から「取得のみ」へ変えた。

## 1. 未解決スレッドを取る — 既定はREST、効率を頼まれたときだけMCP

### 1-1. REST `GET /comments`（既定）

```python
from notion_client import page_id_from_url, get_comments

page_id = page_id_from_url("<ページURL>")
comments = get_comments(page_id, recursive=True)
```

- **`recursive=True` を付ける。** 付けないとページ自体へのコメントだけが返り、本文への
  インラインコメントが落ちる。`GET /comments?block_id=` はそのブロック単位でしか返さないため、
  `get_comments` が本文の全ブロックを辿って1つずつ問い合わせる（子ページは辿らない）
- **時間はブロック数で決まる。** 1ブロック＝1リクエストで、待ちは `notion_request` が見る
  （2026-09-17の実測: 228ブロックで約2分）。呼び出し側で並列化や `time.sleep` を足さない
- 返る各コメントのうち、使うのは次の4つ

| フィールド | 中身 |
|---|---|
| `discussion_id` | スレッドのID。**返信に使う** |
| `parent` | どこへのコメントか。本文なら `block_id`、ページ自体なら `page_id` |
| `created_by` | **`id` と `object` だけ**。人かbotかは `id` を突き合わせて判定する（→ 1-3） |
| `rich_text` | コメント本文 |

- **どの記述への指摘かは、ブロック単位までしか分からない。** 選択範囲の文字列は返らないので、
  `notion_request("GET", f"/blocks/{block_id}")` で対象ブロックを取り、`notion_blocks.block_to_lines`
  で本文を読む。範囲まで要るならMCPの `text-context`（→ 1-2）

### 1-2. MCP `notion-get-comments`（効率を重視するよう頼まれたときだけ）

**使うのは、依頼の中でコメント取得の効率を重視するよう求められたときだけ。**
「効率重視で」「急いで」「手早く」のように、速さや手数の少なさを頼まれた場合が当たる。
**迷ったらRESTにする。** ページが大きいことを理由に、頼まれていないのにMCPへ切り替えない。
解決済みを読むときもこちらを使う（RESTでは読めない）。

```
notion-get-comments(page_id="<page ID>", include_all_blocks=true)
```

- **1回の呼び出しでページ全体が取れる。** RESTのようにブロック数ぶん問い合わせない
- **`include_resolved` を省けば未解決のみ。** `true` にすると解決済みも `resolved="true"` 付きで返る
- **`include_all_blocks: true` を必ず付ける。** 既定はページ直下のスレッドだけで、インラインコメントが落ちる
- **`page_id` はUUIDのみ。** ページURLを渡すと400になるので、URL末尾の32桁を `8-4-4-4-12` へ整形してから渡す。
  ユーザーはURLを貼るだけでよい
- 返る `discussion://<ページID>/<ブロックID>/<discussionID>` の**末尾が `discussion_id`**。これを返信に使う。
  `text-context` にアンカーされた本文が入るので、どの記述への指摘かはこれで分かる

**`notion-fetch(include_discussions=true)` は使わない。** 本文にアンカーの出ないコメント
（Mermaid図など）を取りこぼすうえ、ページ本文を丸ごと読む。同じページで実測して
**fetch=5件 / get-comments=9件**だった。

| | REST `get_comments`（既定） | MCP `notion-get-comments`（例外） |
|---|---|---|
| ページ全体を取る | 本文の全ブロックを1つずつ問い合わせる | 1回 |
| 時間 | ブロック数に比例（228ブロックで約2分） | ほぼ一定 |
| 解決済み | 取れない | `include_resolved` で取れる |
| どの記述への指摘か | ブロック単位まで | 選択範囲の文字列（`text-context`）まで |
| 投稿者の見分け方 | `created_by.id` | `user-url` |

### 1-3. 答えるのは自分宛てのスレッドだけ

投稿者で絞るパラメータはRESTにもMCPにも無く、**取得は全員ぶん返る**（他メンバーのコメントも、
スレッド内の自分の過去の返信も）。絞るのは取ったあと。突き合わせる相手は2つで、どちらも1回引いて使い回す。

| 誰 | 取り方 |
|---|---|
| 使い手本人 | MCP `notion-get-users(user_id="self")` の `id` |
| このスキルのbot（過去の返信） | REST `notion_request("GET", "/users/me")` の `id`（`type` は `"bot"`） |

**使い手本人のIDはMCPでしか取れない。** MCPコネクタは使い手本人のNotionアカウントとして
認証されているので、`self` を聞けば答える（2026-09-17に実測。返る `id` は、コメントの
`user-url` に入っているUUIDと同じもの）。RESTの `GET /users/me` はトークンの持ち主である
Integrationのbotを返す（2026-09-29に実測）。
**スキルにも設定ファイルにも、メールアドレスやユーザーIDを書かない。**

**判定はスレッド単位で、最後のコメントを見る。** RESTなら `discussion_id` でまとめ、
`created_time` が最も新しいものが最後。

| スレッドの最後のコメント | RESTでの見分け方 | MCPでの見分け方 | 扱い |
|---|---|---|---|
| 使い手本人 | `created_by.id` が `self` の `id` と一致 | `user-url` が `user://<self の id>/<メール>` | **返信する**（自分の問いかけが未応答） |
| bot | `created_by.id` が `/users/me` の `id` と一致 | `user-url` が `bot` | **飛ばす**（返信済み） |
| 他のメンバー | どちらとも一致しない | `self` と違うUUID | **飛ばす**（自分宛てとは限らない。答えるならユーザーの指示が要る） |

- **一致する発言でも、内容を書いたのが本人とは限らない。** 公式MCPで投稿すると本人名義になるため
  （→ 手順2）、過去にその経路で返した返信は人の発言として返る

## 2. 頼まれたら返信する — 常にREST `POST /comments`

**返信は、取得をどちらの経路で行っても常にREST。**

```python
create_comment({
    "discussion_id": "<discussion ID>",
    "rich_text": [{"text": {"content": "ご指摘の…"}}],
})
```

**MCPの `notion-create-comment` は使わない。** 取得を例外のMCPで行ったときは、そのまま
同じMCPで返したくなるが、**公式MCPコネクタは使い手本人のNotionアカウントとして
投稿する**ので、Claudeの返信が本人の発言として残る（他スキル経由の実行で実際に発生）。

| 経路 | 認証 | 投稿者 |
|---|---|---|
| REST `create_comment`（`notion_client.py`） | Integrationトークン | **bot**（Integration名）← これで返す |
| MCP `notion-create-comment` | 使い手のNotionアカウント | **使い手本人** ← 使わない |

**見分け方は投稿者名。** 返信後にNotionで自分の名前とアイコンが付いていたら、MCPで投げている。

- **1スレッド＝1リクエスト。** 複数スレッドに答えるならこれを件数ぶん呼ぶ（待ちは `notion_request` が見る）
- **取得した `discussion_id` を先に全部並べてから回す。** 1件読んでは考え…と進めると、
  途中で「残りはどうしますか?」と聞き返して打ち切りやすい
- **投稿者はIntegrationのbot**（`created_by` は `type: "bot"`）。`display_name` を付けても
  **表示名が変わるだけ**で `created_by` はbotのまま。既定（Integration名）で使う。
  **レスポンスの `created_by.type` が `"bot"` かで、botとして入ったことを確かめられる**

## ブロックを作り直すと、そこに付いたコメントは消える

`notion-update-page` の `update_content` は、**表のように行を持つブロックを書き換えるとき、
ブロックごと作り直す**（新しいblock_idになり、古いIDは404）。このとき
**そのブロックにアンカーされたスレッドは、返信する前に消える。**

2026-09-17に、ある表へ列を1つ足しただけでスレッドが1件消えた。`discussion_id` は
取得済みだったが、`POST /comments` を投げる前に対象が無くなっていた。

**コメントのある表を直すときは、順番を変える。**

1. **返信を頼まれているなら、先に返信する。** 直す前にスレッドへ答えを書いておけば、ブロックが作り直されても返信は残る
2. そのうえで表を直す
3. 消えたことに後から気づいたら、**同じ節へページコメントを立て直し、「元のスレッドが消えた」と明記する**
   （黙って新しいスレッドにすると、相手は自分の指摘が無視されたように見える）

**セル1つの文言を直すだけなら消えない。** 消えるのは行数・列数が変わるときと、
表全体を置換したとき。返信を頼まれたスレッドが1件でもあるなら、
**列を足す前に返信を済ませる。**

## APIではできないこと

| やりたいこと | 可否 |
|---|---|
| 既存スレッドへ返信 | ○ |
| ページ・ブロックへコメント | ○ |
| 選択したテキスト範囲に**新しい**スレッドを立てる | **×** |
| コメントを解決する | **×**（画面で行う） |
| 解決済みコメントをRESTで読む | **×**（MCPの `include_resolved` なら読める） |
| コメントが付いた文字範囲をRESTで知る | **×**（ブロック単位まで。MCPの `text-context` なら分かる） |

**準備が足りないときの合図。** 次のときは先へ進まず、README の「セットアップ」をユーザーに案内する。

- 403、または内容の無い部分的なレスポンスが返る → Integrationの **Read comments / Insert comments** が無効（既定はオフ）
- 公式MCPのツール（`notion-get-users` など）が見つからない → 公式MCPが接続されていない
